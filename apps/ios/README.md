# iOS app

SwiftUI shell over the Rust core (`crates/app-core` through the Swift SDK in
`bindings/swift`). The shell renders Core read models, forwards intents and
implements the platform ports; it keeps no business state of its own. Design:
the `approach/mobile-*` decisions in [STATUS.md](../../STATUS.md).

## Build and run

```bash
ISCT_SDK_PROFILE=dev node scripts/bindings/build-ios.mjs --simulator-only
```

```bash
xcodegen generate --spec apps/ios/project.yml
```

Set `CARGO_TARGET_DIR` to a directory shared between worktrees (for example
`~/.cache/isct-target`) and the SDK build reuses the compiled dependency
graph instead of rebuilding it per checkout; the XCFramework and generated
Swift still land under that directory's `native-sdk/`.

Then open `apps/ios/IsctCompanion.xcodeproj` (generated, not committed) and run
the `IsctCompanion` scheme. `--simulator-only` builds the slice for the host's
simulator (x86_64 on Intel Macs, arm64 on Apple silicon); `--device-only`
builds just the iPhone slice for installing on a phone.

A free Personal Team cannot sign the iCloud container, and `CKContainer`
traps at launch without it. Such a build passes an entitlements file with only
`keychain-access-groups` as `CODE_SIGN_ENTITLEMENTS` and adds `ISCT_NO_ICLOUD`
to `SWIFT_ACTIVE_COMPILATION_CONDITIONS`, which opens the session without
iCloud backup. That entitlements file also drops the App Group
`group.app.isctcompanion`, which belongs to team `FB7AL944GK`: the share
extension then cannot save to the inbox and its assignment list stays empty.
Test sharing into the app with a build signed by that team. OCR is
unavailable on the Intel simulator.

## Layout

| Path | Content |
|---|---|
| `IsctCompanion/Core/AppModel.swift` | Owns the `Session`: subscription, read models (`today`, `assignmentBoard`, `scheduleView`, `courseDetail`), intents, lifecycle facts |
| `IsctCompanion/Core/SchoolBrowserHost.swift` | `NativeBrowser`: one resident WKWebView per school site, driven by Core |
| `IsctCompanion/Core/WebRouter.swift` | Which school page is on screen; `openSchool` and the visibility fact |
| `IsctCompanion/Core/KeychainVault.swift` | `NativeVault`; item names come from Core's `vaultItem`, shared with the Mac app through iCloud Keychain |
| `IsctCompanion/Core/NotificationScheduler.swift` | Registers Core's `notificationPlan` with `UNUserNotificationCenter` (64 pending at most) |
| `IsctCompanion/Features/*` | 今日 (class stack and the quarter's assignments) · 時間割 · ウェブ · 設定, course detail |
| `IsctCompanion/Features/Map` | The campus map: an `MKMapView` drawing Core's map page. Core owns the page (`campusMapOpen`, `campusMapSend`, `campusMapSearch`, `campusMapClose`): the room string's targets, what is selected (one way in by stable id for taps, marks, search and course rooms), which building and floor the visible part of the map brings into focus, the card and its Maps links (Apple or Google, the `mapsApp` setting), and where the camera goes; each answer is a scene the screen draws by role in theme colours. The screen reports the part of the map its search bar, card and level picker leave visible, and tells its own camera moves from the person's by its framing lifecycle. Opened full screen from a course's rooms, 今日's next class, or 今日's map button to browse; no route, the blue dot is MapKit's own, asked for when the person taps the position button (when in use only). The data is Isct-Data's `campus-map/v1`, which Core downloads and keeps; until it is stored no map button shows. `yarn sdk:ios` builds the SDK with the `campus-map` feature |
| `IsctCompanion/Resources/Assets.xcassets/CampusMap` | The map's 14 amenity and entrance icons (SVG, template), drawn 28 pt; each amenity's asset is named by Core's amenity key, as is its `campusMap.amenity.<key>` text |
| `IsctCompanion/Design/Generated` | Tokens generated by `yarn design:tokens`; do not edit |

## Not yet

Open items are the slotledger task `ios-open-items` (widgets among them).

UI strings are keyed by namespaced message keys (`settings.reset.caches.title`)
and read at runtime from the desktop's `resources/locales` catalogs
(`Design/Localization.swift`), so the language follows `settings.locale` rather
than the phone's. `en.json` holds every key with its English copy; a test in
`apps/desktop/tests` checks that each key used here exists.
